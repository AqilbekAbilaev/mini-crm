# Для руководителя: как это устроено (без терминов)

Система состоит из двух частей: **сайт**, который видит пользователь, и **база данных** в облачном
сервисе Supabase, где хранятся объекты, задачи и история.

Главное: **все правила записаны в самой базе, а не на сайте.** Сайт — это просто «окно». Даже если
кто-то обойдёт сайт и начнёт слать запросы в базу напрямую (это умеет любой программист), база
проверит каждый запрос и откажет, если у человека нет прав. Это называется RLS — «защита на уровне строк»:
база для каждой записи решает, кому её можно показать или изменить.

**Что не может сделать исполнитель:**
- увидеть чужие задачи и объекты, где у него нет задач;
- создать, отредактировать или удалить задачу или объект;
- сам принять свою задачу или «перепрыгнуть» статус (например, из «Новая» сразу в «Принята»);
- изменить, подделать или удалить историю — её не может править вообще никто, включая постановщика;
- назначить себя постановщиком.

**Постановщик** тоже не может нарушить порядок статусов: принять задачу можно только из «На проверке»,
вернуть на доработку — только с комментарием.

Зарегистрироваться самостоятельно нельзя — пользователей заводит администратор. Секретный
«ключ администратора» хранится только у разработчика и на сайт не попадает.

Проверки не на словах: скрипт `npm run seed` специально пытается всё это сделать от имени исполнителя
и проверяет, что база отказывает.

# Решения и допущения

1. **У задачи всегда есть исполнитель** (поле обязательное) — иначе непонятно, кто берёт её в работу.
   Исполнителем можно назначить только пользователя с ролью «исполнитель».
2. **Смена исполнителя** не меняет статус и не пишется в историю (в ТЗ история — только про статусы).
   Если сменить исполнителя у задачи «В работе», новый исполнитель продолжает с того же статуса.
3. **Создание задачи** пишется в историю как первая запись «— → Новая».
4. **Комментарий** можно оставить при любом переходе; обязателен — только при возврате на доработку.
5. **Удаление объекта, у которого есть задачи, запрещено** — чтобы случайно не потерять задачи и историю.
   Сначала нужно удалить или перенести задачи.
6. **Удаление задачи постановщиком удаляет и её историю.** Через API историю отдельно удалить нельзя;
   исчезает она только вместе с задачей. Если нужен аудит удалённого — заменить на «мягкое» удаление (архив).
7. **Постановщик может редактировать задачу в любом статусе**, включая «Принята».
8. **Имена всех пользователей видны всем** вошедшим (нужно для выбора исполнителя и истории).
   Других данных в профиле нет.
9. Постановщики равноправны: любой постановщик может принять задачу другого постановщика.
10. Роль пользователя хранится в базе и задаётся администратором; сменить её через сайт нельзя.

# Что не успел / можно добавить

- Нет страницы управления пользователями — пользователи и роли через Supabase Dashboard.
- Нет фильтров, поиска и пагинации — при текущих объёмах не нужны.
- Нет обновления в реальном времени (чужие изменения видны после перезагрузки страницы).
- Автотесты — только скрипт проверки безопасности в `scripts/seed.mjs`, UI-тестов нет.
